# Investigation: production backup permissions on StorageBox

Symptom: the first actual daily helper completed 1069 objects and 35 tables in run `20261006T000029Z-5d4265d9`, but StorageBox reports the backup directory, run directory, roles.sql and receipt as mode 0755. chmod 0700 succeeds without changing those synthetic permissions.

Evidence provided by the coordinator: actual findmnt identifies CIFS with `file_mode=0755,dir_mode=0755,nounix`. This invalidates the assumption that Python umask and requested modes protect plaintext roles and data on that mount. Confirmed hypothesis: mount synthesizes permissions and cannot enforce the intended per-file restrictions. Refuted hypothesis: another chmod call can make the plaintext backup private. The coordinator is relocating only the newly created plaintext backup to local private staging; earlier backups and independent Mac restore evidence remain untouched.

Owner: daily backup helper, its tests and operational documentation. Fix direction before implementation: stage all plaintext on a verified local private directory with actual permission and space guards; publish only a streaming AES-256-GCM authenticated encrypted package and a sanitized public receipt. Read the fresh exact 32-byte key from an owner-only local file, never arguments/env/log values. Authenticate and hash-compare all package entries on private readback before atomic success. No production runtime writes, container start/stop/restore or old-backup deletion. Failed plaintext remains only in local private staging; any external incomplete material is ciphertext and sanitized metadata only. Coordinator retains an independent private key copy off the server; loss of the key makes the encrypted backup unrestorable.

Follow-up before test fix: the new whole-flow encrypted-publication test fails with `TypeError: key must be bytes-like`. The actual encryption roundtrip/tamper tests passed; whole backup loop reuses the identifier `key` for an object path and overwrites the encryption key bytes. Confirmed owner/fix direction: use a distinct `encryption_key` variable throughout the backup lifecycle, keep the real whole-flow regression and do not weaken cryptography checks. No production invocation of this draft.

Verification: 15 backup contract tests pass on cryptography 41.0.7, matching the actual host version. Real streaming AES-GCM roundtrip exceeds 1 MiB; wrong key, ciphertext, tag and authenticated metadata all fail, with unauthenticated private validation output removed. Actual key/mode/symlink and local-space guards pass; interrupted encryption leaves only partial ciphertext externally, no public success receipt or plaintext. Whole backup regression publishes only encrypted payload plus sanitized metadata and verifies the original private object manifest; concurrent inventory change publishes nothing. Black, Ruff and diff whitespace checks pass. Runtime invocation now requires --key and supports --staging; coordinator must repeat the real backup before unattended installation. No production calls or commits in this writer task.

Retaining every successful daily plaintext staging copy would eventually exhaust the local filesystem despite encrypted external backups being valid. Confirmed owner/fix direction: remove only the uniquely created private run directory, with its original inode/device and guarded staging parent verified, after full authenticated external readback and successful atomic publication. Failed private stages and pre-existing staging data remain untouched. Record actual cleanup in the sanitized public receipt and summary; a cleanup failure must not be presented as fully successful. Reproductions use owned local tempfile fixtures only. Confirmed hypothesis: exception cleanup assumes output ownership before exclusive creation succeeds; cryptography is not the cause. Owner/fix direction: reject identical source/destination, mark output owned only after successful exclusive creation, and unlink only the same actual inode/device created by this invocation.
